# Touch workspace

The October 30 redesign uses iOS-inspired light surfaces, rounded controls and restrained blue accents. Cashier identity stays visible, the payment area stays fixed, and forms fit the café screen without hiding their actions. Plain Spanish labels and all employee-recovery controls remain intact. No external font download or heavy blur is required.

The default register keeps the original owner's workflow: catalog on the left, current order on the right, item adjustments on tap and payment. The rejected Juniper prototype and original owner register remain available with server environment `POS_REGISTER_UI=prototype` or `POS_REGISTER_UI=owner`; restart the server after changing appearance. The default is `workspace`. All three use the same current checkout, reporting, shift and recovery contracts.

The user's supplied Windows display screenshot shows 1366×768 at 60 Hz and Intel UHD Graphics 620. The café PC reports an i5-8250U and 7.92 GB RAM. Actual scaling, touch calibration and app performance still need measurement. Browser checks target 1366×650 and 1093×560 as conservative working viewports; they are not hardware benchmarks.

The workspace shows products and the current order in two columns, with a fixed total and payment action. Category filters use active catalog categories; Todos restores the complete menu. Search applies within the selected category. Empty favorites do not reserve a product section; administrators keep a compact configuration link. Tap an order line, marked with a pencil, to change quantity, options or preparation notes, or remove it. All modifier groups are visible together. Order type and optional order notes are inside checkout. Common cash payment is one panel; MXN+USD and manual terminal confirmation remain supported. No taxes, sample prices or totals are invented. Inventory is excluded from this candidate at the user's request.

The November 2 usability correction replaces generic stock imagery in the default cashier catalog with compact name/price buttons. Valid configured product photos are still shown; missing or failed photos leave the name and price visible without substituting another product's picture. The original owner/prototype views and other existing consumers retain their illustrative fallback. The 20 bundled WebP thumbnails and source/license record remain available. No database image URLs or sale snapshots are rewritten.

Editing stages quantity together with extras and notes. Guardar cambios commits the complete line in one store update, so cart persistence never saves a half-edited line. Closing with X or Escape discards the staged edit. Opening the editor again starts from the stored line. Quitar remains a separate explicit action. New products use Agregar a la orden. Universal Sin hielo/Sin azúcar shortcuts were removed from this form: manual preparation notes, including previously stored notes, remain editable. Modifier groups explicitly describe their existing optional behavior; no recipe default or new required selection is invented. Tickets has a visible text label and its actions say Reimprimir último / Reimprimir folio, matching their existing print flow.

No runtime dependency was added. The app uses installed system fonts instead of downloadable font files. The new views have no decorative animation, blur, gradients, charts, JavaScript scrolling loop or extra polling. Filtering is memoized, product activation has a stable callback, and offscreen product buttons use native content visibility where supported. These are implementation properties, not claimed café-PC frame-rate measurements.

Sign-in, cash opening and saved-sale confirmation use the same layout. Opening cash can be counted with large denomination buttons; numeric entry preserves fractional dollars. Search/customer/note keyboards are optional. Payment confirmation stays disabled while cash is insufficient or card approval has not been acknowledged. Confirmed sales automatically send customer and barista copies through the local Windows dispatcher. Historical reprints and closing reports use the Windows print dialog.

Admin accounts enter administration through a visible Administración button in the cashier toolbar or at the top of cash opening, and return with Volver a caja. The entry uses its own labeled button rather than the café name. Cashier accounts show only cashier workflows; the server continues to deny their access to admin routes. Login still lands on the cashier screen; navigation is deliberate and stays in the same tab. Administration has four main workflows: Ventas, Caja, Catálogo and Clientes. A secondary Configuración link opens account management and backups, with a printing-recovery entry available for support. There is no persistent sidebar or dashboard. Sales shows a total, date/search controls and ticket rows; payment breakdown and secondary figures are under Desglose. Existing authorization, full-report totals, date semantics, pagination, cancellation and printing handlers remain.

Caja shares navigation between Turno y cortes and Entregas y tipo de cambio. Catálogo shares navigation between Productos y extras and Favoritos de caja. Related pages retain their URLs, handlers and saved-request recovery. Ticket details link to printing recovery; the printing warning and drawer-recovery links remain available. The sales display opens from Ventas. The duplicate cancellation screen and unfinished coupon screen redirect to Ventas, where a selected ticket retains its cancellation action. The informational ticket-settings page redirects to Configuración. These UI redirects do not remove database records or change receipt configuration, reporting, backup or printer-journal contracts.

A pre-workspace UI source snapshot contains the accepted register, prototype, login, app layout/font configuration and administration shell, report controls and sales view. It contains no environment files or database data. For register-only rollback prefer the appearance setting. Restoring the older full Owner-UI-Rollback archive is not a database rollback; keep current migrations and all trading records.

Verification: run `npm test`, `npm run typecheck`, `npm run lint` and `npm run build:verify`. Use isolated loopback fixtures for browser checks. Never use hosted business data for a preview. Check real-menu modifier edits, quantities, notes, refresh recovery, manual card confirmation and drawer totals in the browser. Physical touch accuracy and actual café performance remain site acceptance work.
