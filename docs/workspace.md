# Touch workspace

The default register keeps the original owner's workflow: catalog on the left, current order on the right, item adjustments on tap and payment. The rejected Juniper prototype and original owner register remain available with server environment `POS_REGISTER_UI=prototype` or `POS_REGISTER_UI=owner`; restart the server after changing appearance. The default is `workspace`. All three use the same current checkout, inventory, reporting, shift and recovery contracts.

The user's supplied Windows display screenshot shows 1366×768 at 60 Hz and Intel UHD Graphics 620. CPU/RAM, actual scaling, touch calibration and measured performance remain unknown. Browser checks target 1366×650 and 1093×560 as conservative working viewports; they are not hardware benchmarks.

The workspace shows products and the current order in two columns, with a fixed total and payment action. There are no category tabs, permanent item controls or extra global navigation. Tap an order line to change quantity, options or preparation notes, or remove it. All modifier groups are visible together. Order type and optional order notes are inside checkout. Common cash payment is one panel; MXN+USD and manual terminal confirmation remain supported. No taxes, sample prices, totals or inventory policies are invented.

Product photos keep their existing image URLs and load lazily. The local 82-product menu fixture contains confirmed names/prices but no confirmed photo mapping; no generic stock imagery is substituted. Full-resolution source photos still need appropriate size/decoding checks on the café PC.

No runtime dependency was added. The app uses installed system fonts instead of downloadable font files. The new views have no decorative animation, blur, gradients, charts, JavaScript scrolling loop or extra polling. Filtering/stock lookup is memoized, product activation has a stable callback, and offscreen product buttons use native content visibility where supported. These are implementation properties, not claimed café-PC frame-rate measurements.

Sign-in, cash opening and saved-sale feedback use the same restrained workspace surface. Opening cash can be counted with large denomination buttons; numeric entry preserves fractional dollars. Search/customer/note keyboards are optional. Payment confirmation stays disabled while cash is insufficient or card approval has not been acknowledged. Printing remains a cashier choice in the Windows dialog.

Admin accounts enter administration through a visible Administración button in the cashier toolbar or at the top of cash opening, and return with Volver a caja. The entry uses its own labeled button rather than the café name. Cashier accounts show only cashier workflows; the server continues to deny their access to admin routes. Login still lands on the cashier screen; navigation is deliberate and stays in the same tab. Administration has a short list of four common tools and a collapsed list of remaining options. There is no persistent sidebar or dashboard. Sales shows a total, date/search controls and ticket rows; payment breakdown and secondary figures are under Desglose. Existing authorization, full-report totals, date semantics, pagination, cancellation and printing handlers remain.

A pre-workspace UI source snapshot contains the accepted register, prototype, login, app layout/font configuration and administration shell, report controls and sales view. It contains no environment files or database data. For register-only rollback prefer the appearance setting. Restoring the older full Owner-UI-Rollback archive is not a database rollback; keep current migrations and all trading records.
