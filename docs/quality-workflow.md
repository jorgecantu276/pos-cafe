# Coordinated quality workflow

Use a main coordinator/implementer and a separate read-only reviewer. Add UI,
backend or packaging owners only for separable changed work; four permanent
agents are not required for every task. Review the final integrated revision and
observable evidence. Keep optional cleanup in a separate task.

Define expected product behavior and completion before editing. Preserve current
shared handlers, financial identities, separate client data and existing recovery
contracts. Smoothies uses its own profile, recipe-to-menu flow and local backend.
Historical Café acceptance does not qualify a Smoothies device.

Run relevant functional/regression checks plus required repository CI. Changes to
money, storage, payments, printing, startup/update or recovery need their affected
failure/restart checks. UI changes need real navigation, narrow viewport, keyboard
and legibility checks. Record actual commands/results and untested limits.

Do not demand a full family release rehearsal for a progress report or small local
candidate. Exact package/client qualification and all-three family promotion still
apply at their boundaries. Never manufacture passing evidence from labels.

Reviewer findings should identify a concrete defect and expected outcome.
Independent review may block correctness/regression issues; style preference does
not justify a new framework or indefinite rewrite. No test makes a real charge,
physical print or production migration without its actual authorized scope.

See [historical quality evidence](quality-review.md), [product progress](products/smoothies.md)
and [deployment boundaries](windows-deployment.md). Historical integration/merge
authorizations are not renewed by this procedure.
